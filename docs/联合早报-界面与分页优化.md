## 分页来源与边界

从本机 `.com` 页面实际嵌入的 LoadMoreArticle 组件观察到：queryCode=8、pageSize=27、pageType=sitemap，下一页从 pageNo=2 开始。该组件使用的地址为：

```text
https://zbapi.zbstatic5.com/more/sitemap/8?pageNo=N&pageSize=27
```

该地址是中国频道的官方分页数据来源，不是 `.com.sg` 文章源。详情仍直接请求 `.com`，不递归抓取推荐文章，也不开放任意 API 地址。

在真实窗口验收中发现：未带官网客户端请求校验头时，接口可能因缓存命中返回 JSON，也可能返回空响应。因此补齐公开客户端 Request 模块使用的 x-amz-date / x-auth 校验：输入只有 UTC 时间、GET 方法、固定路径及页码，使用 MurmurHash3 x64_128；不涉及账号、Cookie、私钥或订户内容。保留明确的错误与重试，不将空响应当作“没有更多文章”。签名函数用参考哈希向量、固定时间与不同日期分支测试。

引擎保存 next_page / has_more，失败不推进，追加按文章 ID 去重并保留顺序。客户端不能选择任意 URL 或跳页。SQLite v3 对 v1/v2 增量升级并备份；已加载的列表重启后仍可读取。RPC 用 offset / limit（默认 60，最多 100）分段读取本地内容，避免长列表超过消息上限。

## 并发与缓存正确性

- 正文任务不等待图片。后台图片每次写回比对 fetchedAt，防止旧下载覆盖新正文。
- 图片先完整下载、校验、原子写入，再更新正文；失败不影响文字。
- 清缓存先取消后台图片，再清理，避免图片任务把刚清除的内容写回来。
- 阅读器返回列表不丢已有条目与滚动位置；图片更新事件只影响当前文章。
- API 客户端等待任务结束时立即脱离事件监听，不让异步监听清理阻挡已完成任务。
